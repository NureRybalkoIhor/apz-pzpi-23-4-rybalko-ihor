	2 ЗАВДАННЯ
В цій лабораторній роботі необхідно показати як можна масштабувати бекенд системи для роботи із великим навантаженням. Для цього, можна на вибір: - масштабувати сервер горизонтально - багато копій сервера виконують однакові функції для різних користувачів; - масштабувати сервер вертикально - різні мікросервіси виконують різні функції і масштабуються окремо одне від одного. З технічної точки зору, масштабування можна виконати так: - деплой сервера на Kubernetes кластер, разом із окремим load balancer-ом та базою даних. При цьому треба буде показати коректну роботу системи при збільшенні чи зменшенні кількості подів сервера чи окремих мікросервісів; - деплой в serverless середовище (AWS Lambda, Firebase Cloud Functions або аналогічне). Треба показати що система може зменшувати кількість активних інстансів до 0, збільшувати її зі збільшенням трафіку і все ще коректно функціонувати. - ваш власний спосіб показати що система може масштабуватись. На найвищий бал на цю роботу необхідно провести навантажувальне тестування за допомогою Gatling, JMeter, Locust чи іншого подібного інструмента і показати як зі збільшенням кількості серверів зростає кількість запитів на секунду яку витримує система. 
3 ОПИС ВИКОНАНОЇ РОБОТИ
Під час виконання лабораторної роботи було вирішено завдання проєктування та реалізації підсистеми масштабування бекенду платформи попереднього замовлення їжі FoodPreOrder. Основна мета роботи полягала у демонстрації горизонтального масштабування серверної частини системи та проведенні навантажувального тестування для підтвердження зростання пропускної здатності зі збільшенням кількості інстансів.
3.1 Стратегія масштабування
Обрано стратегію горизонтального масштабування - розгортання кількох ідентичних екземплярів API-сервера за єдиним балансувальником навантаження. Така стратегія є доцільною для stateless REST API на ASP.NET Core, оскільки кожен под не зберігає стан між запитами - автентифікація реалізована через JWT-токени, а стан сесії зберігається виключно у базі даних.
Технічною основою масштабування є розгортання у кластері Kubernetes (Docker Desktop) з такою конфігурацією: чотири репліки API-контейнера (foodpreorder-api), один под бази даних MS SQL Server 2022 та сервіс типу NodePort як точка входу для зовнішнього трафіку на порту 30082. Балансування навантаження між подами забезпечується вбудованим механізмом Kubernetes Services за алгоритмом round-robin.
3.2 Технічні рішення
Конфігурація Kubernetes визначена у файлі kubernetes.yaml і містить чотири ресурси. ConfigMap зберігає змінні оточення спільні для всіх реплік: рядок підключення до бази даних із параметром Max Pool Size=100, JWT-ключ та режим оточення. PersistentVolumeClaim об'ємом 5 ГБ забезпечує збереження даних бази даних між перезапусками пода, що є критично важливим для цілісності даних. Deployment для API визначає чотири репліки з лімітами ресурсів 1 CPU та 896 МБ RAM на под, а також livenessProbe та readinessProbe через TCP-сокет для автоматичного перезапуску та керування трафіком. Service типу NodePort забезпечує маршрутизацію зовнішніх запитів до будь-якого доступного пода.
Паралельно реалізовано конфігурацію Docker Compose у файлі docker-compose.yaml для локального розгортання: п'ять реплік API-сервера за Nginx reverse proxy з рівномірним розподілом запитів та MS SQL Server з persistent volume. Nginx налаштований з оптимізованими параметрами проксі: HTTP/1.1 keep-alive з'єднання та таймаути 60 секунд.
3.3 Аналіз вузьких місць
При збільшенні навантаження першим вичерпуваним ресурсом є пул з'єднань до бази даних - параметр Max Pool Size=100 означає що при 4 репліках система підтримує до 400 одночасних з'єднань із БД. Другим вузьким місцем є сам под бази даних, оскільки MS SQL Server розгорнуто в єдиному екземплярі - він стає спільним для всіх API-реплік і при значному навантаженні стає обмежуючим фактором. Третім ресурсом що вичерпується є оперативна пам'ять пода бази даних (ліміт 2 ГБ), оскільки SQL Server активно використовує пам'ять для кешування даних.
3.4 Навантажувальне тестування
Тестування проводилося за допомогою інструменту Locust із файлом locustfile.py. Сценарій імітує поведінку реальних користувачів: запити до трьох ключових ендпоінтів із вагами відповідно до реального розподілу трафіку - GET /api/restaurants (вага 10), GET /api/dishes (вага 9), GET /api/orders (вага 8). Між запитами симулюється час обдумування від 1 до 3 секунд. Параметри тесту: 270 віртуальних користувачів, швидкість появи 30 користувачів на секунду, хост http://localhost:30082.
Інтерфейс Locust доступний за адресою http://localhost:8089 і відображає графіки RPS, часу відповіді та кількості помилок у реальному часі. Для демонстрації залежності між масштабуванням та пропускною здатністю тест проводився послідовно при 1, 2 та 4 репліках API-сервера шляхом зміни параметра replicas у kubernetes.yaml та повторного застосування маніфесту командою kubectl apply -f kubernetes.yaml.
3.5 Панель керування масштабуванням
У веб-клієнті платформи реалізовано адміністративну панель масштабування (вкладка «Scaling & Workload» в AdminDashboard). Панель дозволяє інтерактивно налаштовувати параметри через слайдери та перемикачі: кількість реплік бекенду (1–15), ліміти CPU (0.1–4 ядра) та RAM (128–8192 МБ), параметри HPA (мін./макс. репліки, цільове завантаження CPU), пул з'єднань БД та параметри навантажувального тестування (кількість VU, швидкість появи, тривалість, профіль навантаження). На основі введених значень у реальному часі генеруються конфігураційні файли docker-compose.yaml, kubernetes.yaml та locustfile.py, які можна завантажити безпосередньо з інтерфейсу або автоматично зберегти у вибрану папку через File System Access API.

4 ВИСНОВКИ
Під час виконання лабораторної роботи було проведено повний цикл проєктування та реалізації підсистеми масштабування бекенду платформи попереднього замовлення їжі FoodPreOrder. Основною метою роботи була демонстрація горизонтального масштабування серверної частини системи та підтвердження зростання пропускної здатності при збільшенні кількості інстансів за допомогою навантажувального тестування.
Ключовим технічним рішенням стало розгортання API-сервера у кластері Kubernetes (Docker Desktop) у вигляді чотирьох реплік за сервісом типу NodePort. Конфігурація Kubernetes визначена декларативно у файлі kubernetes.yaml і охоплює ConfigMap зі спільними змінними оточення, PersistentVolumeClaim для збереження даних бази даних між перезапусками подів, Deployment з налаштованими пробами живості та готовності, а також Service для балансування вхідного трафіку. Паралельно підготовлено конфігурацію Docker Compose із п'ятьма репліками API за Nginx reverse proxy для локального розгортання без Kubernetes.
Навантажувальне тестування проводилося за допомогою Locust із сценарієм, що імітує реальний розподіл запитів між ендпоінтами системи. Порівняльне тестування при 1, 2 та 4 репліках підтвердило лінійне зростання RPS пропорційно до кількості подів, що свідчить про відсутність суттєвих вузьких місць у прикладному коді та ефективність обраної стратегії масштабування. Основним виявленим вузьким місцем є єдиний под бази даних MS SQL Server - при значному навантаженні саме він стає обмежуючим фактором, а не API-сервери.
Додатковим результатом роботи стала реалізація адміністративної панелі керування масштабуванням у веб-клієнті. Вкладка «Scaling & Workload» дозволяє інтерактивно налаштовувати параметри розгортання та в реальному часі генерувати конфігураційні файли kubernetes.yaml, docker-compose.yaml та locustfile.py з автоматичним збереженням у вибрану директорію через File System Access API. Такий підхід забезпечує зручну інтеграцію між конфігурацією інфраструктури та веб-інтерфейсом системи. Отримана реалізація підтверджує ефективність горизонтального масштабування для stateless REST API та готова до демонстрації на захисті.
